Decisión de Arquitectura: Timeline único de media con PyAV

Navigation
  • Other language version
  • Manual core ES
  • Decisión previa: sender directo libndi

Después de mover el sender a libndi directo, la deriva larga seguía apareciendo. Eso cambió el foco: el problema ya no parecía estar solo en el wrapper, sino en cómo el streamer reconstruía el tiempo de audio y vídeo.

1. Problema

El modelo anterior desacoplaba audio y vídeo:

  • vídeo paced por fps,
  • audio decodificado completo y troceado según el índice de frame de vídeo.

Ese enfoque introducía dos relojes implícitos y abría la puerta a drift acumulado en sesiones largas, especialmente con fps fraccionales o cambios de señal.

2. Decisión

La nueva arquitectura usa PyAV como reader unificado del contenedor. Cada evento de audio o vídeo sale con su tiempo de media y el runtime usa un solo reloj de reproducción.

3. Cambios aplicados

  • media_reader.py introduce el timeline único.
  • stream_video.py consume MediaVideoEvent y MediaAudioEvent.
  • utils.py crea el sender con clocks NDI desactivados para evitar doble autoridad temporal.
  • requirements.txt fija av==17.1.0.

4. Qué se gana

  • menos lógica manual propensa a error,
  • mejor comportamiento con 23.976/24/59.94/60 fps,
  • menos acoplamiento entre cadencia de vídeo y entrega de audio,
  • una arquitectura mucho más legible para el equipo.

5. Tradeoffs

  • entra una dependencia nueva: PyAV,
  • hay que validar bien su instalación en las máquinas objetivo,
  • ffmpeg.py queda como helper legacy y podrá limpiarse después.

6. Estado de validación actual

  1. NDI Monitor,
  2. Unity Editor,
  3. Unity AVP Simulator,
  4. build en Apple Vision Pro.

Resultado observado: el streamer funciona correctamente en estos targets tras el cambio a timeline unificado con PyAV.

7. QA recomendada a partir de aquí

  1. mantener sesiones largas como prueba de regresión operativa,
  2. seguir comparando NDI Monitor y Unity cuando aparezca una fuente nueva o sospechosa,
  3. repetir la validación con señales a 24/23.976 y 60/59.94 fps,
  4. revisar cambios de source en caliente y reinicios del sender como casos base de regresión.

8. Resumen

PyAV no se introduce para complicar el proyecto, sino para quitar la parte más sospechosa del modelo anterior: reconstruir audio desde la rejilla temporal del vídeo en lugar de respetar el tiempo real del contenedor.
