Architecture Decision: Direct libndi A/V Sender

Updated: 2026-06-18

Status: implemented in code and functionally validated in NDI Monitor, Unity Editor, Unity AVP Simulator, and Apple Vision Pro device build.

Navigation: Core ES manual · Core EN manual · ES version

1. Context

After long-run tests, the Python sender showed systematic A/V drift: after roughly 20-30 minutes, audio ended up 1-2 seconds behind video. The issue reproduced both in Unity and NDI Monitor, so Unity was no longer the primary suspect.

2. Previous architecture

The A/V sender used cyndilib as a high-level NDI wrapper. The rest of the pipeline was already relatively direct: ffprobe for metadata, ffmpeg for decode, numpy for buffers/overlays, and a metadata backchannel already close to direct libndi via ctypes.

3. What was tried before changing the base layer

  1. manual pacing with a monotonic clock,
  2. exact per-frame audio windows,
  3. manual control of video looping,
  4. explicit timestamps and timecodes,
  5. different NDI clock configurations,
  6. combinations of internal and external clocks.

None of these variants reliably removed long-run drift.

4. Decision

The high-level cyndilib A/V sender is replaced with a minimal direct sender built on top of libndi.

This is a scoped migration, not a full rewrite. Decode, overlays, metadata and the backchannel remain; only the A/V sending layer changes.

5. What we gain

  • explicit control over NDIlib_send_create_t, NDIlib_video_frame_v2_t and NDIlib_audio_frame_v3_t,
  • less implicit wrapper buffering,
  • less opaque behavior in the critical path,
  • better instrumentation and debugging potential,
  • one less mandatory Python dependency in runtime.

6. What we lose

  • high-level convenience abstractions,
  • more ownership of native structs, lifecycle and compatibility,
  • stronger need for long-run QA and platform validation.

7. Exact migration scope

  • ndi_native.py: libndi runtime and direct sender.
  • utils.py: native sender factory.
  • stream_video.py: updated A/V orchestration.
  • extensions/backchannel/receiver.py: compatibility with native or legacy sender.
  • requirements.txt: mandatory Python dependency reduced to numpy.

8. Dependency state

Mandatory: numpy==2.3.5, ffmpeg, ffprobe, libndi.

Optional/legacy: cyndilib is no longer required for A/V sending. It may remain installed as a fallback or as a legacy comparison path.

9. Observed versions

  • Python: 3.11.0
  • NumPy: 2.3.5
  • FFmpeg / FFprobe: 8.1
  • Detected NDI runtime: NDI SDK APPLE 6.2.1.0

10. Open risks

  • drift may still persist even with a direct sender,
  • behavior may differ across macOS, NDI Monitor and other receivers,
  • the real issue may live in media timing or audio segmentation.
Correct interpretation: moving to direct libndi removes a major uncertainty source, but it does not by itself guarantee that drift disappears. The purpose is to isolate the real cause using a more transparent architecture.

11. Current validation status

  1. NDI Monitor,
  2. Unity Editor,
  3. Unity AVP Simulator,
  4. Apple Vision Pro device build.

Observed result: after simplifying the sender and then moving the A/V timeline to PyAV, the current behavior is correct on all of these targets.

12. Recommended QA from this point

  1. keep long-session soak tests as an operational regression check,
  2. continue using NDI Monitor as the fastest reference when a source looks suspicious,
  3. repeat the matrix with 24/23.976 and 60/59.94 fps signals,
  4. treat sender restarts and hot source changes as standard regression cases.
